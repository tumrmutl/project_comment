## อ่านตรงนี้ก่อน

### สิ่งที่กลุ่มทำได้ดีและควรรักษาไว้

1. **แบ่งผู้ใช้เป็น 3 บทบาทชัดเจน** ได้แก่ นักศึกษา อาจารย์ และผู้ดูแลระบบ ทำให้เห็นผู้มีส่วนเกี่ยวข้องหลักของระบบ
2. **ขอบเขตมีโครงระบบย่อยที่ใช้เป็นขอบเขตอ้างอิงที่อนุมัติได้** ไม่ได้เขียนเป็นชื่อระบบกว้าง ๆ เพียงบรรทัดเดียว จึงสามารถนำไปตามรอยข้อกำหนดและกรณีทดสอบ ของสิ่งที่ตกลงไว้เดิมได้
3. **บทที่ 4 มีภาพการทำงานหลายส่วนของระบบ** แสดงให้เห็นว่ากลุ่มลงมือพัฒนาจริงและมีเนื้อหาเพียงพอที่จะจัดใหม่เป็นหลักฐานการทดสอบ
4. **เลือกโดเมนที่มีประโยชน์ต่อหลักสูตรและนักศึกษา** เรื่องการมองเห็นทักษะกับสายอาชีพมีคุณค่า เพียงต้องระวังการตีความคะแนนให้ตรงกับสิ่งที่ข้อมูลวัดได้จริง

### สถานะของเล่ม

**ยังมีประเด็นสำคัญที่ควรแก้ก่อนส่งหรือสอบ แต่มีทางแก้ชัดเจนและไม่จำเป็นต้องรื้อระบบทั้งหมด**

งานหลักคือทำให้คำกล่าวอ้างในเล่มพอดีกับหลักฐาน แก้ข้อมูลอ้างอิงให้ตรวจย้อนกลับได้ ทำระบบและสถาปัตยกรรมให้ครบตามขอบเขตที่อนุมัติ และเปลี่ยนภาพหน้าจอกับรหัสสถานะ API ให้เป็นชุดทดสอบที่มีผลที่คาดหวังและผลจริง เมื่อสี่ส่วนนี้ดีขึ้น คุณภาพเล่มจะเปลี่ยนอย่างเห็นได้ชัด

### ความหมายของระดับข้อเสนอแนะ

- **วิกฤต — ต้องแก้ก่อนส่ง:** กระทบแกนวิธี ความน่าเชื่อถือ หรือทำให้ข้อสรุปยังยืนยันไม่ได้
- **สำคัญ — ควรแก้ให้ครบ:** กระทบคุณภาพบทออกแบบ/การทดลอง แต่มีฐานงานเดิมให้ต่อยอด
- **เล็กน้อย — ไล่แก้รอบรูปเล่ม:** คำผิด เลขหัวข้อ คำบรรยายรูป/ตาราง หรือความไม่สม่ำเสมอ
- **ข้อเสนอเพิ่มเติม — ทางเลือกยกระดับ:** ทำเมื่อประเด็นจำเป็นปิดครบและยังมีเวลา

## เริ่มแก้จาก 5 งานนี้

1. **ทำตารางรายการอ้างอิง 24 รายการ** แล้วตรวจชื่อ ผู้แต่ง ปี แหล่งตีพิมพ์ หน้า และ DOI จากหน้าผู้จัดพิมพ์ จากนั้นใส่เลขอ้างอิงกลับเข้าเนื้อหาบทที่ 1–2
2. **ตกลงคำอธิบายวิธีคำนวณใหม่** ว่าผลจากเกรดเป็น “ค่าประมาณระดับทักษะจากผลการเรียน” พร้อมทำตัวอย่างคำนวณ 2 กรณี และระบุข้อจำกัด
3. **ตรวจความสอดคล้องกับขอบเขตที่อนุมัติ** ขอบเขตระบุ Express.js จึงควรทำและแสดงสถาปัตยกรรมให้ครบตามนั้น หากมีหนังสือ/บันทึกอนุมัติให้เปลี่ยนเป็น SvelteKit ฝั่งเซิร์ฟเวอร์ แล้ว จึงใช้อ้างอิงการเปลี่ยนแปลงและทำบทที่ 2–5 ให้ตรงกับฉบับที่อนุมัติ
4. **สร้างกรณีทดสอบจากขอบเขต** อย่างน้อยทุกกระบวนการทำงานหลักและทุกบทบาท โดยมี ข้อมูลนำเข้า ผลที่คาดหวัง ผลจริง ผ่าน/ไม่ผ่าน และหลักฐาน
5. **ซ่อมรูปเล่มด้วยเขตข้อมูลอัตโนมัติของคำบรรยายรูปและตาราง** ให้เลขรูป/ตารางกลับเป็น 3.x และ 4.x แล้วขยายแผนภาพ/หน้าจอที่อ่านไม่ออก

> ถ้าเวลาน้อย ให้ทำข้อ 1–4 ก่อน ส่วนการเกลาภาษาและความสวยงามทำเป็นรอบท้าย

## คำตัดสินภาพรวม

**ต้องแก้สาระสำคัญก่อนส่งหรือสอบ — แก้ได้โดยใช้แผน 5 รอบท้ายรายงาน**

ตัวระบบมีขอบเขตฟังก์ชันค่อนข้างชัดและบทที่ 4 แสดงหน้าจอครบหลายบทบาท ซึ่งเป็นฐานที่นำมาแก้ต่อได้ดี สิ่งที่ยังขาดคือหลักฐานสำหรับข้อสรุปเชิงวิศวกรรมและเชิงวิจัย โดยเฉพาะความเที่ยงตรงของวิธีแปลงเกรดเป็นระดับทักษะ ความสอดคล้องของสถาปัตยกรรม Express.js/SvelteKit กับขอบเขตที่อนุมัติ ความถูกต้องของบรรณานุกรม การอ้างอิงในตัวบท และการทดสอบ API ประเด็นเหล่านี้แก้ได้ด้วยการทำสิ่งที่อนุมัติไว้ให้ครบ ลดคำกล่าวอ้างให้ตรงข้อมูล ตรวจแหล่งต้นฉบับ และจัดหลักฐานทดสอบใหม่ โดยไม่ต้องเปลี่ยนขอบเขตเดิม

#### METH-01 — การแปลงเกรดเป็น “ระดับทักษะจริง” ยังไม่มีความเที่ยงตรง

- ระดับ: **วิกฤต**
- ตำแหน่ง: PDF 25–33 / เล่ม 8–16; PDF 76 / เล่ม 59; PDF 104–109 / เล่ม 87–92
- สิ่งที่พบ: ระบบนำเกรดรายวิชา 0–4 ไปปรับสเกลตามระดับสูงสุดของ Bloom แล้วเปรียบเทียบกับเกณฑ์อาชีพ จากนั้นใช้ถ้อยคำว่าเป็นระดับทักษะจริง ถูกต้อง แม่นยำ ยุติธรรม และปราศจากอคติ
- หลักฐาน: เกรดรายวิชาเป็นคะแนนรวมจากหลายผลลัพธ์การเรียนรู้ ไม่ได้พิสูจน์ว่าผู้เรียนทำทักษะแต่ละรายการได้ในระดับเดียวกัน ส่วนระดับ Bloom เป็นระดับกระบวนการคิดของกิจกรรมหรือผลลัพธ์การเรียนรู้ ไม่ใช่หน่วยวัดความชำนาญโดยอัตโนมัติ
- ผลกระทบ: ผลการวิเคราะห์ช่องว่าง อาจดูเป็นตัวเลขที่แม่นยำ แต่ไม่มีความตรงเชิงโครงสร้าง รองรับ ทำให้ข้อสรุปหลักของโครงงานอ่อนลง
- แนวทางแก้:
  1. เปลี่ยนถ้อยคำจาก “ระดับทักษะจริง” เป็น “ค่าประมาณระดับทักษะจากผลการเรียน” จนกว่าจะมีการพิสูจน์
  2. นิยามตัวแปรทุกตัว หน่วย ช่วงค่า และเหตุผลที่เลือกสมการ
  3. แสดงตัวอย่างคำนวณตั้งแต่เกรด–รายวิชา–ทักษะ–ระดับ Bloom–เกณฑ์อาชีพ–ค่าช่องว่างอย่างน้อย 2 กรณี รวมกรณีขอบเขต
  4. สร้างเกณฑ์อ้างอิงจาก เกณฑ์ให้คะแนนงานปฏิบัติหรือคะแนนผู้เชี่ยวชาญ แล้วเปรียบเทียบผลระบบกับค่าจริงอ้างอิง
  5. รายงาน MAE/RMSE หรือค่าความสอดคล้อง ตามชนิดข้อมูล พร้อมช่วงความเชื่อมั่น และวิเคราะห์กรณีผิดพลาด
  6. ทำการวิเคราะห์ความไว ว่าเมื่อการจับคู่ รายวิชา–ทักษะหรือระดับ Bloom เปลี่ยน ผลลัพธ์เปลี่ยนมากเพียงใด

- ฉบับขั้นต่ำที่ควรแก้: ลดคำว่า “ทักษะจริง/ปราศจากอคติ” เป็น “ค่าประมาณจากผลการเรียน” ทำตัวอย่างคำนวณ และเขียนข้อจำกัดให้ชัด หากยังไม่มีเวลาเก็บ ค่าจริงอ้างอิง ใหม่
- อ่านต่อ:
  - [Standards for Educational and Psychological Testing](https://www.testingstandards.net/uploads/7/6/6/4/76643089/9780935302356.pdf) — อ่านบท ความตรงของการวัด เพื่อเข้าใจว่าการตีความคะแนนต้องมีหลักฐานรองรับ แล้วนำหลักนี้ไปเขียนข้อจำกัดของวิธีในบทที่ 2, 3 และ 5
  - [MinMaxScaler documentation](https://scikit-learn.org/stable/modules/generated/sklearn.preprocessing.MinMaxScaler.html) — ใช้ตรวจสูตรและช่วงค่าในบทที่ 2 แต่ต้องจำไว้ว่า การปรับช่วงข้อมูล เปลี่ยนสเกล ไม่ได้พิสูจน์ว่าคะแนนวัด “ทักษะจริง”

#### METH-02 — SFIA 7 ระดับกับ Bloom 6 ระดับยังเชื่อมกันไม่ชัด

- ระดับ: **วิกฤต**
- ตำแหน่ง: PDF 25–30 / เล่ม 8–13
- สิ่งที่พบ: เล่มนำ SFIA และ Bloom มาใช้ร่วมกัน แต่ไม่พบตารางการจับคู่ ระหว่างกรอบทั้งสอง และไม่อธิบายว่า “ระดับความรับผิดชอบ” ของ SFIA เท่ากับ “ระดับพุทธิพิสัย” ได้อย่างไร
- ผลกระทบ: การเปรียบเทียบความสามารถนักศึกษากับความต้องการของอาชีพอาจเป็นการเทียบคนละมิติ
- แนวทางแก้: ระบุว่ากรอบใดใช้กับตัวแปรใด แยก ความซับซ้อนทางความคิด ออกจาก ความชำนาญ/ความรับผิดชอบ ถ้าจำเป็นต้องเชื่อมกันให้สร้างเกณฑ์การจับคู่ ผ่านผู้เชี่ยวชาญและรายงานวิธีหาความตรงเชิงเนื้อหา เช่น IOC/CVI พร้อมเกณฑ์ตัดสิน
- ฉบับขั้นต่ำที่ควรแก้: ทำตาราง 3 คอลัมน์ว่า Bloom ใช้วัดอะไร, SFIA ใช้อธิบายอะไร และระบบนำค่าทั้งสองมาเชื่อมกันด้วยกฎใด หากยังไม่มีหลักฐานรองรับกฎ ให้บอกว่าเป็นสมมติฐานของต้นแบบ
- อ่านต่อ: [SFIA 9 — Levels of responsibility](https://sfia-online.org/en/sfia-9/responsibilities) อธิบายว่า 7 ระดับของ SFIA เน้นความรับผิดชอบ ความรับผิดชอบ และผลกระทบในการทำงาน ให้นำคำจำกัดความนี้ไปตรวจว่ากำลังเทียบกับ Bloom คนละมิติหรือไม่

#### METH-03 — แหล่งที่มาของเกณฑ์ทักษะของอาชีพยังไม่ตรวจสอบได้

- ระดับ: **สำคัญ**
- ตำแหน่ง: PDF 19–20 / เล่ม 2–3; PDF 54–60 / เล่ม 37–43; PDF 86–94 / เล่ม 69–77
- สิ่งที่พบ: ระบบเปิดให้อาจารย์กำหนดสายอาชีพและระดับทักษะ แต่ยังไม่พบวิธีคัดเลือกผู้เชี่ยวชาญ จำนวนผู้เชี่ยวชาญ วันที่อ้างอิงตลาดแรงงาน หรือกระบวนการทบทวนเกณฑ์

#### ARCH-01 — สถาปัตยกรรมขัดกันระหว่างบท

- ระดับ: **วิกฤต**

- สิ่งที่พบ: ขอบเขตระบุ Node.js + Express.js รูปสถาปัตยกรรมและบทที่ 4 ยังสื่อว่ามี ระบบหลังบ้าน แยก แต่หัวข้อ 3.6 และบทที่ 5 ระบุว่าใช้ SvelteKit ฝั่งเซิร์ฟเวอร์ และตัด Express.js ออก
- ผลกระทบ: ผู้อ่านไม่ทราบ หน่วยที่นำระบบขึ้นใช้งาน, เส้นทางคำขอ และ ขอบเขตของ API ที่เกิดขึ้นจริง การทดสอบและแบบจำลองภัยคุกคาม จึงไม่ตรงระบบ
- แนวทางแก้: ถือ Node.js + Express.js ในบทที่ 1 เป็น ขอบเขตที่อนุมัติ ที่ต้องส่งมอบก่อน ตรวจซอร์สและการนำระบบขึ้นใช้งาน จริง แล้วดำเนินการตามกรณีต่อไปนี้
- ฉบับขั้นต่ำที่ควรแก้:
  1. เปิดซอร์สโค้ดและการนำระบบขึ้นใช้งาน เพื่อทำรายการจุดรับ คำขอ/กระบวนการ ที่มีจริง พร้อมเทียบทีละข้อกับขอบเขตที่อนุมัติ
  2. ถ้ามีกระบวนการ Express แยกจริง ให้ทำให้ครบ วาดเป็นหน่วยที่นำระบบขึ้นใช้งาน คนละกล่อง แสดงโพรโทคอล/พอร์ต, การยืนยันตัวตน/เซสชัน, เส้นทางคำขอ และหลักฐานการทดสอบ
  3. ถ้าปัจจุบันใช้เฉพาะ SvelteKit ฝั่งเซิร์ฟเวอร์ แต่ **ไม่มีหลักฐานอนุมัติเปลี่ยน** ให้รายงานสถานะตามจริงว่ายังไม่ครบ/ขัดแย้งกับขอบเขตที่อนุมัติ และทำ Express.js ให้ครบตามที่ตกลงไว้
  4. ถ้ามีหลักฐานว่าอาจารย์หรือคณะกรรมการอนุมัติการเปลี่ยนเป็น SvelteKit แล้ว ให้แนบ/อ้างเลขเอกสารหรือบันทึกการอนุมัติ เหตุผล ผลกระทบ วันที่ และฉบับ จากนั้นวาด สถาปัตยกรรมของระบบที่พัฒนาจริง และทำบทที่ 2–5 ให้ตรงกับขอบเขตฉบับที่อนุมัติ โดยไม่เขียนเหมือนขอบเขตเดิมไม่เคยมีอยู่
  5. ตรวจบทที่ 1, 3, 4, 5 ด้วยคำค้น Express, REST, การทำงานของแบบฟอร์ม และฝั่งเซิร์ฟเวอร์ แล้วทำตาราง “ข้อกำหนดเดิม → หลักฐานการทำครบ/หลักฐานอนุมัติเปลี่ยน → ตำแหน่งในเล่ม”

#### UX-01 — บทออกแบบ UX/UI แสดงผลลัพธ์หน้าจอรวม แต่ไม่แสดงกระบวนการออกแบบ

- ระดับ: **สำคัญ**
- ตำแหน่ง: PDF 61–64 / เล่มหน้า 44–47
- สิ่งที่พบ: มีเพียงรายชื่อหน้าและภาพรวม 8/9/12 หน้าจอ ภาพแต่ละหน้าจอเล็ก ไม่มีหมายเลข หมายเลขกำกับบนภาพ และไม่พบ บุคลิกจำลองผู้ใช้, กระบวนการทำงาน, สถาปัตยกรรมสารสนเทศ, แบบร่างหน้าจอ, เหตุผลการออกแบบ หรือ หลักการด้านความง่ายในการใช้งาน
- ผลกระทบ: เป็นการแสดง GUI ที่ทำแล้ว มากกว่าหลักฐานความสามารถในการออกแบบ
- แนวทางแก้:
  1. แสดง เส้นทางการใช้งานปัจจุบัน และ งานเป้าหมาย ของนักศึกษา อาจารย์ ผู้ดูแล
  2. ทำ แผนผังเว็บไซต์/สถาปัตยกรรมสารสนเทศ และ เส้นทางการใช้งาน ของงานสำคัญ
  3. แสดง แบบร่างหน้าจอระดับหยาบ ก่อน ส่วนติดต่อผู้ใช้ที่มีรายละเอียดสูง พร้อมเหตุผลการจัดลำดับข้อมูล
  4. แยกทีละหน้าหรือทีละ กระบวนการทำงาน ให้ภาพใหญ่ ใส่ ป้ายกำกับ 1, 2, 3…บนภาพจริง แล้วอธิบายว่าแต่ละจุดคืออะไร กดแล้วไปไหน มีเงื่อนไขใด
  5. บันทึก สถานะไม่มีข้อมูล/กำลังโหลด/ข้อผิดพลาด/สำเร็จ/ไม่มีสิทธิ์, พฤติกรรมการแสดงผลหลายขนาดหน้าจอ, ตำแหน่งโฟกัสจากแป้นพิมพ์, ความเปรียบต่าง, ป้ายกำกับแบบฟอร์ม และข้อความช่วยแก้ ข้อผิดพลาด ที่มีอยู่ในระบบตามขอบเขตเดิม หากสถานะใดยังไม่มีและไม่ได้อยู่ใน ขอบเขตที่อนุมัติ ให้ระบุเป็นข้อจำกัดหรืองานอนาคต ไม่ยกระดับเป็นฟังก์ชันบังคับใหม่
  6. แสดง ระบบการออกแบบ เช่นสี ตัวอักษร ระยะห่าง ส่วนประกอบ และเหตุผลด้าน การเข้าถึงสำหรับผู้ใช้ทุกกลุ่ม
- ถ้ายังไม่เคยทำ UX มาก่อน ให้เริ่มเพียง กระบวนการทำงาน “นักศึกษาเลือกอาชีพและอ่าน ช่องว่างทักษะ” วาดกล่องทีละขั้นก่อน แล้วค่อยจัดทำหลักฐานของ กระบวนการทำงาน อาจารย์/ผู้ดูแลที่อยู่ในขอบเขตเดิม ไม่ต้องสร้าง บุคลิกจำลองผู้ใช้ จำนวนมากถ้าไม่มีข้อมูลผู้ใช้จริง

  - [10 Usability Heuristics](https://www.nngroup.com/articles/ten-usability-heuristics/) — ใช้ข้อ การมองเห็นสถานะของระบบ การป้องกันข้อผิดพลาด และการช่วยผู้ใช้แก้ไขข้อผิดพลาด ตรวจ แบบร่างหน้าจอ/หน้าจอทีละ กระบวนการทำงาน

- สิ่งที่พบ:
  - แผนภาพอีอาร์ (ER) ตัวเล็กจน จำนวนความสัมพันธ์และชื่อเขตข้อมูล อ่านยาก
  - ตารางเชื่อม Course_skills, Job_skills และ Student_grades ไม่ระบุ ข้อบังคับคีย์หลักแบบผสม/ค่าไม่ซ้ำ ชัดเจน
  - หัวข้อคีย์นอก ของ Course_skills กล่าวถึง skill_id แต่ไม่กล่าวถึง course_id
  - พจนานุกรมข้อมูล ไม่มีข้อกำหนดการเป็นค่าว่าง ค่าเริ่มต้น ค่าไม่ซ้ำ ข้อบังคับการตรวจสอบ และดัชนี, เมื่อปรับปรุง/ลบข้อมูล และเหตุผลชนิดข้อมูล
  - Student_grades ไม่มีภาคเรียน ปีการศึกษา หรือครั้งที่ลงทะเบียน จึงรองรับประวัติเกรดซ้ำได้ไม่ชัด
  - Users เก็บ grade_letter และ grade_point ซ้ำกัน เสี่ยงข้อมูลไม่ตรง
  - Job.name_job เป็น VARCHAR(20) ซึ่งสั้นเกินไปสำหรับหลายชื่อตำแหน่ง
- แนวทางแก้: วาด ER ใหม่พร้อม จำนวนความสัมพันธ์/การมีหรือไม่มีก็ได้ ระบุ PK/FK/UK และ กฎทางธุรกิจ แล้วขยาย พจนานุกรมข้อมูล ให้ครบ เงื่อนไขบังคับ พร้อมตัวอย่าง คำสั่ง SQL DDL หรือชุดคำสั่งปรับโครงสร้างฐานข้อมูล ที่ตรงกับระบบจริง
- ฉบับขั้นต่ำที่ควรแก้: ระบุ คีย์หลัก/คีย์นอก/ค่าไม่ซ้ำ/การอนุญาตให้เป็นค่าว่าง ของทุกตารางเชื่อม อธิบายเหตุผลเก็บ grade_letter กับ grade_point และเพิ่มภาคเรียน/ปีการศึกษาหากระบบต้องเก็บประวัติ
- อ่านต่อ: [MySQL 8.4 — FOREIGN KEY Constraints](https://dev.mysql.com/doc/refman/8.4/en/create-table-foreign-keys.html) ใช้ตรวจชนิดข้อมูลของคีย์ ความเข้ากันได้ของดัชนี และพฤติกรรม ON DELETE/ON UPDATE ก่อนแก้ พจนานุกรมข้อมูล

#### API-02 — ความหมาย HTTP 401/403 และเลขหัวข้อผิด

- ระดับ: **เล็กน้อย**
- ตำแหน่ง: PDF 70–71 / เล่มหน้า 53–54
- สิ่งที่พบ: 401 อธิบายกว้างว่าไม่ได้รับอนุญาต ส่วน 403 เขียนไม่ครบ ความหมายที่ควรใช้คือ 401 = ยังไม่ผ่าน/ไม่มีข้อมูลยืนยันตัวตนที่ใช้ได้ และ 403 = ยืนยันตัวตนแล้วแต่ไม่มีสิทธิ์ทำรายการ อีกทั้งเลขหัวข้อ 3.1.7.1–3.1.7.2 ควรตรวจให้ตรงกับ 3.7
- แนวทางแก้: แก้คำจำกัดความและเลขหัวข้ออัตโนมัติทั้งชุด
- อ่านต่อ: [RFC 9110 — HTTP Semantics](https://www.rfc-editor.org/rfc/rfc9110.html#name-401-unauthorized) อ่านหัวข้อ 401 และ 403 แล้วใช้ถ้อยคำจากความหมายมาตรฐานในการแก้ตาราง 3.12

#### EVAL-02 — จำนวนข้อแบบประเมินไม่ตรงกัน

#### EVAL-03 — แบบประเมินยังผสม ความง่ายในการใช้งาน กับ ความถูกต้อง/ความมั่นคงปลอดภัย

#### EVAL-01 — ความพึงพอใจไม่ใช่หลักฐานยืนยัน ความถูกต้อง, ความมั่นคงปลอดภัย หรือ ประสิทธิผล

- ระดับ: **สำคัญ**
- ตำแหน่ง: PDF 71–75 / เล่มหน้า 54–58 และ PDF 99–103 / เล่มหน้า 82–86
- สิ่งที่พบ: คำถามและการอภิปรายผลนำความเห็นของผู้ใช้ไปสนับสนุนความถูกต้องของการคำนวณ ความปลอดภัย ความเสถียร และความสามารถในการแก้ช่องว่างทักษะ
- หลักฐาน: ผู้ตอบแบบประเมินสามารถรายงานว่าผล “ดูเข้าใจง่าย” หรือ “รู้สึกว่าสอดคล้อง” แต่ไม่สามารถตรวจสูตร สิทธิ์เข้าถึง ช่องโหว่ หรือความแม่นยำเทียบค่าจริงได้จากการใช้งานทั่วไป
- ผลกระทบ: เกิดการสรุปข้ามประเภทข้อมูล ทำให้ข้ออ้างหลักของโครงงานเกินกว่าหลักฐาน
- แนวทางแก้: แยกข้อสรุปเป็น 4 ชุด ได้แก่ การทำงานตามหน้าที่ ความถูกต้อง จาก เกณฑ์ตัดสินผลทดสอบ, ความตรงของแบบจำลอง จากค่าจริงอ้างอิง/ผู้เชี่ยวชาญ, ความมั่นคงปลอดภัย/สมรรถนะ จากการวัดเชิงเทคนิค และ ความง่ายในการใช้งาน/ความพึงพอใจ จากผู้ใช้ ห้ามนำค่าเฉลี่ยความพึงพอใจชุดเดียวไปยืนยันทุกด้าน

#### TRACE-01 — ผลการทดลองยังไม่จัดตามขอบเขตและ เกณฑ์ยอมรับ

#### TEST-01 — การทดสอบ API ไม่เพียงพอสำหรับคำว่าเสถียรและปลอดภัย

- ระดับ: **วิกฤต**
- ตำแหน่ง: PDF 97–98 / เล่มหน้า 80–81
- สิ่งที่พบ: ตารางแสดง จุดเชื่อมต่อ API, วิธีเรียกและรหัสสถานะ เท่านั้น ไม่ระบุข้อมูลนำเข้า ผลที่คาดหวัง ผลตอบกลับ, เงื่อนไขตรวจผล, สภาพแวดล้อม, จำนวนรอบ, เวลาตอบกลับ, ผู้ใช้พร้อมกัน, อัตราข้อผิดพลาด หรือ กรณีทดสอบความมั่นคงปลอดภัย
- ผลกระทบ: สถานะ 200/201 เพียงครั้งเดียวไม่ใช่หลักฐาน สมรรถนะ ความเชื่อถือได้ หรือความมั่นคงปลอดภัย ส่วน 401 ไม่พิสูจน์ว่า การกำหนดสิทธิ์ของทุกบทบาทถูกต้อง
- แนวทางแก้:
  1. ทำกรณีทดสอบที่มีรหัส พร้อม เงื่อนไขก่อนทดสอบ/ข้อมูลนำเข้า/ผลที่คาดหวัง/ผลจริง/ผ่าน–ไม่ผ่าน
  2. เพิ่ม กรณีผิดพลาดและการทดสอบตารางไขว้ตามบทบาท
  3. วัด p50/p95 เวลาหน่วง, อัตราการประมวลผล, อัตราข้อผิดพลาด ภายใต้จำนวน ผู้ใช้พร้อมกัน ที่กำหนด
  4. ทดสอบ การแทรกคำสั่ง การควบคุมสิทธิ์ที่บกพร่อง การโจมตีเซสชัน/CSRF การจำกัดอัตราการเรียกใช้ สิทธิ์ในการส่งออกแฟ้ม และการเปิดเผยข้อมูลอ่อนไหว
  5. รายงานเครื่องมือ เวอร์ชัน สเปกเครื่อง ฐานข้อมูล และจำนวนรอบเพื่อทำซ้ำได้

- ถ้ายังไม่เคยเขียน กรณีทดสอบ ให้เริ่มจากรูปแบบนี้หนึ่งแถวแล้วขยาย:

| รหัสการทดสอบ | ผู้ใช้/เงื่อนไข | ข้อมูลนำเข้า/การกระทำ | ผลที่คาดหวัง | ผลจริง | ผล |
|---|---|---|---|---|---|
| AUTH-ออกจากระบบ-01 | นักศึกษาที่เข้าสู่ระบบแล้ว | กดออกจากระบบ แล้วเปิดหน้าที่ต้องเข้าสู่ระบบซ้ำ | เซสชันถูกยกเลิกและระบบพาไปหน้าเข้าสู่ระบบ | กรอกจากผลจริง | ผ่าน/ไม่ผ่าน |

- อ่านต่อ: [OWASP Web Security Testing Guide — Latest](https://owasp.org/www-project-web-security-testing-guide/latest/README) ให้เลือกเฉพาะหัวข้อ การยืนยันตัวตน การกำหนดสิทธิ์ การจัดการเซสชัน การตรวจข้อมูลนำเข้า และการทดสอบ API ที่ตรงระบบ ไม่จำเป็นต้องทำทุกกรณีในคู่มือ แต่ต้องบอกว่าทดสอบอะไรและผลเป็นอย่างไร

## แบบการประเมินที่แนะนำให้ใช้แทน/เพิ่ม

### 1. การทดสอบการทำงานตามหน้าที่

- แยก ชุดการทดสอบ ตาม รหัสขอบเขต และ ผู้ใช้งาน
- ทุกกรณีมี รหัสการทดสอบ, เงื่อนไขก่อนทดสอบ, ข้อมูลนำเข้า ขั้นตอน, ผลที่คาดหวัง ผลจริง ผ่าน/ไม่ผ่าน, หลักฐาน และ ข้อบกพร่อง
- ครอบคลุม กรณีปกติ, ค่าขอบเขต, รูปแบบไม่ถูกต้อง, ข้อมูลซ้ำ, ไม่มีสิทธิ์, การแก้ไขพร้อมกัน, ฐานข้อมูลไม่พร้อมใช้งาน และการกู้คืน

### 2. การตรวจสอบความถูกต้อง ของการคำนวณทักษะ

- สร้างชุดตัวอย่างที่ผู้เชี่ยวชาญให้ค่าทักษะอ้างอิงจากหลักฐานปฏิบัติ
- ใช้ผู้เชี่ยวชาญมากกว่าหนึ่งคนและรายงานเกณฑ์ฉันทามติหรือ ค่าความสอดคล้องระหว่างผู้ประเมิน
- เปรียบเทียบค่าระบบกับค่ามาตรฐานด้วย ตัวชี้วัด ที่เหมาะสม
- วิเคราะห์ กรณีประเมินสูงเกินจริง/ต่ำเกินจริง และสาเหตุ
- ทดสอบผลกระทบของเกรดซ้ำ รายวิชาที่ การจับคู่ หลายทักษะ และการเปลี่ยนระดับ Bloom

### 3. การประเมินความง่ายในการใช้งาน

- จำนวนรวม 30 คนขึ้นไปใช้ได้ในฐานะการทดสอบเชิงสำรวจ แต่ต้องแบ่งตาม ผู้ใช้งาน และรายงาน n ต่อ งาน/ข้อ
- อาจารย์ 2 คนและผู้ดูแล 3 คนยังน้อยเกินไปสำหรับการสรุปกว้าง ควรเพิ่มผู้ใช้ในบทบาทดังกล่าว หรือระบุว่าเป็น การตรวจตามขั้นตอนโดยผู้เชี่ยวชาญ/การประเมินเชิงคุณภาพเพื่อปรับปรุงงาน
- ให้ผู้ใช้ทำ งาน จริง เช่น เลือกอาชีพ ดู ช่องว่าง หาเหตุผลของคะแนน แก้ การจับคู่ และ ส่งออกข้อมูล
- เก็บ ความสำเร็จของงาน, เวลาที่ใช้จนเสร็จ, จำนวนข้อผิดพลาด, จำนวนครั้งที่ต้องขอความช่วยเหลือ และ SUS/UMUX-Lite
- เก็บความเห็นปลายเปิด สกัดประเด็น และระบุสิ่งที่ปรับแก้จากผล

### 4. สมรรถนะ และ ความมั่นคงปลอดภัย

- กำหนดภาระงาน และเกณฑ์ก่อนทดสอบ เช่น p95 เวลาหน่วง, อัตราการประมวลผล, อัตราข้อผิดพลาด และจำนวน ผู้ใช้พร้อมกัน
- ทดสอบ การกำหนดสิทธิ์ ตารางไขว้ ทุก จุดเชื่อมต่อ API และทุกบทบาท
- ตรวจ กรณีตาม OWASP อย่างน้อย การแทรกคำสั่ง การควบคุมสิทธิ์ที่บกพร่อง การโจมตีเซสชัน/CSRF และการเปิดเผยข้อมูลอ่อนไหว, การจำกัดอัตราการเรียกใช้ และ สิทธิ์ในการส่งออก
- รายงาน สภาพแวดล้อม, รุ่นซอฟต์แวร์ ข้อมูลตั้งต้น และเครื่องมือ/สคริปต์ และวิธีทำซ้ำ

## แผนแก้เล่มแบบเป็นรอบ

### รอบที่ 1 — หยุดความเสี่ยงด้านความถูกต้อง

1. ตรวจบรรณานุกรมทั้ง 24 รายการจาก DOI/ผู้จัดพิมพ์และเขียนบทงานวิจัยใหม่จากต้นฉบับ
2. ใส่ การอ้างอิงในตัวบททุกนิยาม สมการ รูป สถิติ และข้อค้นพบ
3. กำหนดสถานะของค่าทักษะว่าเป็น “ค่าประมาณ” และออกแบบการตรวจสอบความถูกต้อง
4. ทำ Express.js ให้ครบตามขอบเขตที่อนุมัติ หรือแนบหลักฐานการอนุมัติเปลี่ยนเป็น SvelteKit แล้วทำบทที่ 2–5 ให้ตรงกับขอบเขตฉบับที่อนุมัติอนุมัติ

### รอบที่ 2 — ทำบทที่ 3 ให้เป็นงานออกแบบ

1. ทำการติดตามความสอดคล้องของข้อกำหนด, แผนภาพภาพรวมเชิงแนวคิด แผนภาพองค์ประกอบ และแผนภาพการนำระบบขึ้นใช้งาน
2. ตรวจ ความสมดุลของแผนภาพบริบท/DFD และขยายรูปให้อ่านได้
3. วาด ER พร้อม ข้อบังคับ และแก้ พจนานุกรมข้อมูล
4. เพิ่มหลักฐาน UX กระบวนการ: กระบวนการทำงาน, IA, แบบร่างหน้าจอ, สถานะต่าง ๆ, การเข้าถึงสำหรับผู้ใช้ทุกกลุ่ม และภาพมีหมายเลขกำกับ
5. ทำข้อกำหนดการเชื่อมต่อ API และแบบจำลองภัยคุกคาม

### รอบที่ 3 — สร้างหลักฐานบทที่ 4

1. ทำกรณีทดสอบตามขอบเขตทุกข้อ
2. ทดสอบ ความตรงของวิธีคำนวณ แยกจาก ความง่ายในการใช้งาน
3. ทำการทำงานตามหน้าที่ของ API, สมรรถนะ และการทดสอบความมั่นคงปลอดภัย พร้อมข้อมูลดิบ
4. ตรวจข้อมูลผู้ตอบ 35 คนใหม่ รายงาน n, SD และการกระจาย
5. เพิ่มกราฟและสรุปความคิดเห็นจากผู้ใช้ ที่นำไปแก้ระบบ

### รอบที่ 4 — เขียนส่วนต้นและบทที่ 5 ใหม่

1. เขียนบทคัดย่อไทยจากผลจริง แล้วแปล/ตรวจเทียบอังกฤษ
2. เขียนบทที่ 5 ตามวัตถุประสงค์และขอบเขต พร้อมตาราง ครบ/บางส่วน/ไม่สำเร็จ
3. อภิปรายผลเทียบทฤษฎีและงานวิจัย ไม่กล่าวเกินหลักฐาน
4. ระบุข้อจำกัดและ ภัยคุกคามต่อความตรงของการวัด

### รอบที่ 5 — ตรวจรูปเล่มก่อนส่ง

1. ซ่อมคำบรรยายรูป/ตาราง/เขตข้อมูล แล้วปรับปรุงสารบัญทั้งหมด
2. ขยายแผนภาพ, ER และภาพหน้าจอให้ตัวหนังสืออ่านได้ พร้อมป้ายกำกับ
3. ตรวจคำศัพท์ คำย่อ เชิงอรรถ อภิธานศัพท์ และคำผิดจากตารางข้างต้น
4. ตรวจเลขหน้า การอ้างโยง ลิงก์ คิวอาร์โค้ด และข้อมูลส่วนบุคคล
5. ส่งออกเป็น PDF ใหม่และตรวจแบบทีละหน้า อีกหนึ่งรอบ

## รายการตรวจสอบสำหรับนักศึกษา

ติ๊กเมื่อแก้ในไฟล์ต้นฉบับแล้ว ตรวจ PDF ที่ส่งออกใหม่ และให้สมาชิกอีกคนเปิดตรวจซ้ำ

### ส่วนต้นและบทคัดย่อ

- [ ] ปรับคำกล่าวผลให้ไม่เกินหลักฐานและระบุข้อจำกัดสั้น ๆ
- [ ] แก้บทคัดย่ออังกฤษหลังฉบับไทยนิ่ง แล้วตรวจตัวเลข/ศัพท์ให้ตรงกันทุกค่า (ABSTRACT-02)
- [ ] ตรวจชื่อโครงงาน ชื่อปริญญา ผู้จัดทำ อาจารย์ และปีการศึกษาให้ตรงทุกหน้า
- [ ] แก้คำอธิบาย new_min/new_max ในรายการสัญลักษณ์ (FRONT-01)

### บทที่ 1 บทนำ

- [ ] เพิ่มหลักฐานขนาดหรือผลกระทบของ ช่องว่างทักษะพร้อมการอ้างอิง และปีข้อมูล (CH1-01)
- [ ] เขียนช่องว่างของวิธีเดิม/ระบบเดิมและเหตุผลที่แนวทางนี้น่าจะช่วยได้
- [ ] แยกวัตถุประสงค์การสร้าง การคำนวณ/ศึกษา และการประเมิน พร้อมตัวชี้วัด (CH1-02)
- [ ] คงข้อความและรหัสขอบเขตที่อนุมัติ แล้วทำตารางขยายความ ผู้ใช้งาน ข้อมูลนำเข้า กระบวนการ, ผลลัพธ์ และหลักฐานการทดสอบ แยกต่างหากโดยไม่เปลี่ยนสิ่งส่งมอบ (CH1-03)
- [ ] ทำ Express.js ให้ครบตามขอบเขตที่อนุมัติ หรือแนบหลักฐานอนุมัติการเปลี่ยนแปลง ก่อนทำ Express.js/SvelteKit ให้ตรงกันทุกบท (ARCH-01)
- [ ] แตก โครงสร้างการแบ่งงาน (WBS) จากขอบเขตทุกข้อ พร้อมสิ่งส่งมอบ และเกณฑ์การเสร็จสมบูรณ์ (CH1-04)
- [ ] ปรับประโยชน์ให้เป็นผลจากระบบที่ใช้ได้จริงและไม่อ้างผลที่ยังไม่ได้วัด (CH1-05)

### บทที่ 2 ทฤษฎีและงานที่เกี่ยวข้อง

- [ ] วาดภาพรวมเชิงแนวคิดใหม่ให้เห็น ข้อมูลนำเข้า → การประมวลผล → เกณฑ์อาชีพ → ช่องว่าง → ผลลัพธ์ (CH2-01)
- [ ] ขยายภาพให้ตัวอักษรอ่านได้และอธิบายทีละองค์ประกอบ
- [ ] เขียนท้ายทุกทฤษฎีว่า “นำมาใช้ที่ใดในโครงงาน” และตัดหัวข้อที่ไม่ได้ใช้ (CH2-02)
- [ ] แยกความหมาย Bloom, SFIA และความชำนาญ พร้อมกฎการจับคู่/ข้อจำกัด (METH-02)
- [ ] ตรวจสูตร Min–Max นิยามตัวแปร และทำตัวอย่างคำนวณจากข้อมูลจริงอย่างน้อย 2 กรณี
- [ ] เพิ่มตารางเปรียบเทียบเทคโนโลยีด้วยเกณฑ์ของโครงงาน (CH2-03)
- [ ] อ่านงานวิจัยจากต้นฉบับและกรอก ปัญหา/ข้อมูล/วิธี/ตัวชี้วัด/ผล/ข้อจำกัด/วิธีนำมาใช้ (REF-04)
- [ ] สังเคราะห์ช่องว่างงานวิจัย หลังตาราง ไม่จบด้วยบทสรุปเรียงเรื่อง (CH2-04)
- [ ] ใส่เลขอ้างอิง หลังข้อความ นิยาม สมการ รูป และผลวิจัยทุกจุด (REF-02)

### บทที่ 3 การวิเคราะห์และออกแบบ

- [ ] สรุปวิธีเก็บข้อกำหนด ผู้ให้ข้อมูล ปัญหาหลัก และการแปลงเป็นข้อกำหนด (CH3-01)
- [ ] แก้ข้อความแบ่งกลุ่มตาม “อายุ” ให้ตรงกับการแบ่งตามบทบาท หรือแสดงหลักฐานอายุ (CH3-02)
- [ ] วาดแผนภาพองค์ประกอบและแผนภาพการนำระบบขึ้นใช้งานให้ตรงกับขอบเขตเดิมที่อนุมัติ หรือขอบเขตฉบับใหม่ที่มีหลักฐานอนุมัติแล้ว (ARCH-01)
- [ ] ตรวจแผนภาพบริบท/DFD ว่ามี 5 หรือ 6 กระบวนการ และตรวจความสมดุล ทุกระดับ (DFD-01)
- [ ] แก้ชื่อ/คำบรรยายรูป 3.12 และกระบวนการที่คัดลอกชื่อผิด (DFD-02)
- [ ] ขยายแผนภาพบริบท DFD, สถาปัตยกรรม และ ER ให้อ่านได้เมื่อพิมพ์จริง (VIS-01)
- [ ] เพิ่มเส้นทางการใช้งาน, แบบร่างหน้าจอ, สถานะต่าง ๆ และเหตุผล UX ก่อนภาพ GUI สำเร็จ (UX-01)
- [ ] ใส่หมายเลขกำกับบนภาพและอธิบายการโต้ตอบทีละหมายเลข
- [ ] แก้ ER/พจนานุกรมข้อมูล ให้มี PK, FK, UK, การอนุญาตให้เป็นค่าว่าง, เงื่อนไขบังคับ และประวัติเกรด (DB-01)
- [ ] อธิบายการเก็บ/หมดอายุ/ใช้ครั้งเดียว/การจำกัดอัตราการเรียกใช้ ของ OTP และตรวจข้อมูลส่วนบุคคล (DB-02)
- [ ] เพิ่มข้อกำหนดการเชื่อมต่อ API: คำขอ, ผลตอบกลับ, การตรวจสอบความถูกต้อง, บทบาท, ข้อผิดพลาด และตัวอย่าง (API-01)
- [ ] แยกแผนทดสอบ ความถูกต้อง, ความตรงของการวัด, สมรรถนะ, ความมั่นคงปลอดภัย และ ความง่ายในการใช้งาน (EVAL-01/EVAL-03)
- [ ] ตรวจจำนวนคำถามแบบประเมินให้เป็นฉบับเดียวกัน 28 หรือ 29 ข้อ (EVAL-02)

### บทที่ 4 ผลการพัฒนาและผลทดลอง

- [ ] เปิดบทด้วย การติดตามความสอดคล้อง: รหัสขอบเขต → การออกแบบ → การทดสอบ → หลักฐาน → ผล (TRACE-01)
- [ ] เปลี่ยนภาพหน้าจอสำคัญให้เป็น กระบวนการทำงานพร้อม ข้อมูลนำเข้า/การกระทำ/ผลที่คาดหวัง/ผลจริง/ผ่าน–ไม่ผ่าน (CH4-01)
- [ ] ใส่หมายเลขกำกับ 1, 2, 3 บนภาพจริงและขยายข้อความ UI ให้อ่านได้
- [ ] เพิ่มกรณีทดสอบ API ทั้ง ข้อมูลถูกต้อง ข้อมูลไม่ถูกต้อง ไม่มีสิทธิ์ และ ตารางไขว้ตามบทบาท (TEST-01)
- [ ] ทดสอบการออกจากระบบ ให้ครบตามจุดเชื่อมต่อ API ที่ออกแบบไว้ หรือแก้จำนวน จุดเชื่อมต่อ API (TEST-02)
- [ ] รายงาน x/N และจำนวนรอบแทนคำว่า “100%” ที่ไม่มีตัวหาร (TEST-03)
- [ ] เรียก CSV ว่า “การส่งออกข้อมูล”; ถ้าจะเรียกว่าการสำรองข้อมูล ต้องมี การทดสอบกู้คืนข้อมูล (TEST-04)
- [ ] ตรวจข้อมูลผู้ตอบ 35 คนและแก้ร้อยละอุปกรณ์ให้กลับเป็นจำนวนคนเต็ม (DATA-01)
- [ ] รายงาน จำนวนผู้ตอบ ค่าเฉลี่ย ส่วนเบี่ยงเบนมาตรฐาน/การกระจาย และแยกนักศึกษา–อาจารย์–ผู้ดูแล (DATA-02)
- [ ] แก้เกณฑ์ช่วงคะแนนที่ซ้ำ/ขัดกัน (DATA-03)
- [ ] เพิ่มกราฟที่มีชื่อแกน หน่วย และจำนวนผู้ตอบ และสรุปความคิดเห็นจากผู้ใช้ → สิ่งที่ปรับระบบ (DATA-04)
- [ ] ใช้ผลความพึงพอใจสรุปเฉพาะการรับรู้ของผู้ใช้ ไม่ใช้ยืนยันความแม่นยำ/ปลอดภัย (DATA-05)

### บทที่ 5 สรุปและข้อเสนอแนะ

- [ ] สรุปทีละวัตถุประสงค์ด้วยหลักฐานและตัวเลขจากบทที่ 4
- [ ] เพิ่มตารางขอบเขต ทั้งหมด/ครบ/บางส่วน/ไม่พบหลักฐาน พร้อมรหัสการทดสอบ (CH5-01)
- [ ] อภิปรายว่าผลสอดคล้องหรือขัดกับทฤษฎีและงานวิจัยใด เพราะอะไร (CH5-02)
- [ ] ตัดคำกล่าวเรื่องลดเวลาหน่วง/เพิ่มความมั่นคงปลอดภัย หากไม่มีเกณฑ์เปรียบเทียบ หรือเพิ่มผลการทดลอง (CH5-03)
- [ ] เขียนข้อจำกัดเรื่องกรอกเกรดและการจับคู่โดยผู้เชี่ยวชาญ แล้วลดระดับข้อสรุปให้ตรงกัน (CH5-04)
- [ ] ตรวจให้ตัวเลขสำคัญตรงกับบทคัดย่อและบทที่ 4

### บรรณานุกรมและงานวิจัย

- [ ] ตรวจรายการทั้ง 24 ชิ้นจาก DOI/หน้าผู้จัดพิมพ์ ไม่แก้เฉพาะ 4 ตัวอย่างที่รายงานพบ (REF-01)
- [ ] แก้ชื่อ ผู้แต่ง ปี วารสาร/ประชุม เล่ม ฉบับ หน้า และ DOI ให้ตรง
- [ ] ตรวจรายการหมายเลข 14 เพิ่ม; หากหาต้นฉบับไม่ได้ให้เปลี่ยนแหล่งหรือแสดงหลักฐาน
- [ ] ตรวจว่า การอ้างอิง ทุกหมายเลขถูกเรียกใช้ในเนื้อหาและไม่มีรายการเกิน
- [ ] ใช้แหล่งต้นฉบับ/ทางการแทนบล็อกหรือ GitHub Topics หรือภาพจากเว็บทั่วไปเมื่อทำได้ (REF-03)
- [ ] ระบุผลเชิงตัวเลขและข้อจำกัดของงานที่เกี่ยวข้อง ไม่สรุปเพียงหัวข้อกว้าง

### ภาษา รูป แผนภาพ และรูปเล่ม

- [ ] ซ่อมเขตข้อมูลอัตโนมัติของคำบรรยายรูปและตาราง ให้รูป/ตารางเป็นเลข 3.x และ 4.x แล้วปรับปรุงเขตข้อมูลทั้งหมด (FMT-01)
- [ ] แก้เลขหัวข้อ 3.1.7.1/3.1.7.2 และ HTTP 401/403 (API-02)
- [ ] แก้คำผิดจากตารางรายการคำผิดด้วยการค้นหา/แทนที่ แบบตรวจบริบท
- [ ] กำหนดคำไทย–อังกฤษ–คำย่อครั้งแรกและใช้รูปเดียวทั้งเล่ม (TERM-01)
- [ ] ทำอภิธานศัพท์/ประมวลศัพท์ และใช้เชิงอรรถเฉพาะคำที่ต้องอธิบาย ณ หน้านั้น (TERM-02)
- [ ] ตรวจว่าทุกรูปอ่านได้ที่ขนาดพิมพ์จริง มีแหล่งที่มา/คำบรรยายรูปหรือตาราง และถูกกล่าวถึงในเนื้อหา
- [ ] ตรวจ คิวอาร์โค้ด, คลังซอร์สโค้ด/ป้ายรุ่น/คอมมิต และความยินยอมก่อนเผยข้อมูลส่วนบุคคล (APP-01)
- [ ] ส่งออกเป็น PDF ใหม่แล้วให้สมาชิกที่ไม่ได้จัดหน้าเปิดตรวจทุกหน้าหนึ่งรอบ

## เกณฑ์พร้อมส่งรอบถัดไป

เล่มควรกลับมาตรวจรอบใหม่เมื่อมีครบอย่างน้อยดังนี้:

- บรรณานุกรมและการอ้างอิง ตรวจจากต้นฉบับครบ
- วิธีคำนวณลดระดับคำกล่าวอ้างหรือมี การตรวจสอบความถูกต้อง รองรับ
- สถาปัตยกรรมตรงกับขอบเขตที่อนุมัติและตรงกันทุกบท
- ตารางติดตามความสอดคล้อง และ กรณีทดสอบ ครบขอบเขต
- ผล API มี ผลที่คาดหวัง/ผลจริง และหลักฐาน สมรรถนะ/ความมั่นคงปลอดภัย ตามที่อ้าง
- ผลประเมินมี n ต่อข้อ, SD/การกระจาย และแก้ข้อมูลร้อยละอุปกรณ์
- แผนภาพ/ER/UX อ่านได้ที่ขนาดพิมพ์จริงและมีคำอธิบายทีละส่วน
- บทคัดย่อมีผลเชิงตัวเลข และบทที่ 5 มีตารางสรุปขอบเขต
- หมายเลขรูป ตาราง หัวข้อ และคำผิดถูกแก้ทั้งเอกสาร
