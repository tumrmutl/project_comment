## อ่านตรงนี้ก่อน

### สิ่งที่กลุ่มทำได้ดีและควรรักษาไว้

1. **แบ่งผู้ใช้เป็น 3 บทบาทชัดเจน** ได้แก่ นักศึกษา อาจารย์ และผู้ดูแลระบบ ทำให้เห็นผู้มีส่วนเกี่ยวข้องหลักของระบบ
2. **ขอบเขตมีโครงระบบย่อยที่ใช้เป็น baseline ได้** ไม่ได้เขียนเป็นชื่อระบบกว้าง ๆ เพียงบรรทัดเดียว จึงสามารถนำไปตามรอย requirement และ test case ของสิ่งที่ตกลงไว้เดิมได้
3. **บทที่ 4 มีภาพการทำงานหลายส่วนของระบบ** แสดงให้เห็นว่ากลุ่มลงมือพัฒนาจริงและมี material เพียงพอที่จะจัดใหม่เป็นหลักฐานการทดสอบ
4. **เลือกโดเมนที่มีประโยชน์ต่อหลักสูตรและนักศึกษา** เรื่องการมองเห็นทักษะกับสายอาชีพมีคุณค่า เพียงต้องระวังการตีความคะแนนให้ตรงกับสิ่งที่ข้อมูลวัดได้จริง

## สถานะขอบเขตของ Project นี้

เล่มนี้เป็น **Project** จึงถือขอบเขตที่ตกลงและอนุมัติแล้วในบทที่ 1 เป็น **baseline คงที่** รายงานฉบับนี้ไม่แนะนำให้นักศึกษาเพิ่ม ลด ตัด หรือเปลี่ยนขอบเขตเพื่อแก้ปัญหาในเล่ม

- คำว่า “เพิ่ม” ใน Comment หมายถึงเพิ่มคำอธิบาย Diagram ตารางตามรอย test case หรือหลักฐานเพื่อยืนยันสิ่งที่อยู่ในขอบเขตเดิม ไม่ได้หมายถึงเพิ่มฟังก์ชันของระบบ
- หากพบว่าสิ่งที่พัฒนาจริงไม่ตรงขอบเขตเดิม ให้ทำให้ระบบครบตามขอบเขตเดิมเป็นทางเลือกแรก
- หากเคยได้รับอนุมัติให้เปลี่ยน implementation/technology แล้ว ให้แนบหรืออ้างเอกสารอนุมัติ พร้อมเหตุผล ผลกระทบ วันที่ และฉบับของ baseline จากนั้นจึงทำบทที่ 2–5 ให้ตรงกัน ห้ามแก้ข้อความขอบเขตย้อนหลังโดยไม่มีหลักฐานการอนุมัติ
- แนวคิดหรือฟีเจอร์ที่อยู่นอก baseline ให้เก็บเป็น “งานอนาคต” และไม่ถือเป็น Checklist บังคับของ Project ปัจจุบัน

### สถานะของเล่ม

**ยังมีประเด็นสำคัญที่ควรแก้ก่อนส่งหรือสอบ แต่มีทางแก้ชัดเจนและไม่จำเป็นต้องรื้อระบบทั้งหมด**

งานหลักคือทำให้คำกล่าวอ้างในเล่มพอดีกับหลักฐาน แก้ข้อมูลอ้างอิงให้ตรวจย้อนกลับได้ ทำระบบและสถาปัตยกรรมให้ครบตาม baseline ที่อนุมัติ และเปลี่ยนภาพหน้าจอกับรหัสสถานะ API ให้เป็นชุดทดสอบที่มี expected/actual result เมื่อสี่ส่วนนี้ดีขึ้น คุณภาพเล่มจะเปลี่ยนอย่างเห็นได้ชัด

### ความหมายของระดับ Comment

- **Critical — ต้องแก้ก่อนส่ง:** กระทบแกนวิธี ความน่าเชื่อถือ หรือทำให้ข้อสรุปยังยืนยันไม่ได้
- **Major — ควรแก้ให้ครบ:** กระทบคุณภาพบทออกแบบ/การทดลอง แต่มีฐานงานเดิมให้ต่อยอด
- **Minor — ไล่แก้รอบรูปเล่ม:** คำผิด เลขหัวข้อ caption หรือความไม่สม่ำเสมอ
- **Suggestion — ทางเลือกยกระดับ:** ทำเมื่อประเด็นจำเป็นปิดครบและยังมีเวลา

## เริ่มแก้จาก 5 งานนี้

1. **ทำตารางรายการอ้างอิง 24 รายการ** แล้วตรวจชื่อ ผู้แต่ง ปี แหล่งตีพิมพ์ หน้า และ DOI จากหน้าผู้จัดพิมพ์ จากนั้นใส่เลขอ้างอิงกลับเข้าเนื้อหาบทที่ 1–2
2. **ตกลงคำอธิบายวิธีคำนวณใหม่** ว่าผลจากเกรดเป็น “ค่าประมาณระดับทักษะจากผลการเรียน” พร้อมทำตัวอย่างคำนวณ 2 กรณี และระบุข้อจำกัด
3. **ตรวจความสอดคล้องกับ baseline ที่อนุมัติ** ขอบเขตระบุ Express.js จึงควรทำและแสดงสถาปัตยกรรมให้ครบตามนั้น หากมีหนังสือ/บันทึกอนุมัติให้เปลี่ยนเป็น SvelteKit server-side แล้ว จึงใช้อ้างอิงการเปลี่ยนแปลงและทำบทที่ 2–5 ให้ตรงกับฉบับที่อนุมัติ
4. **สร้าง test case จากขอบเขต** อย่างน้อยทุก flow หลักและทุกบทบาท โดยมี input, expected, actual, pass/fail และหลักฐาน
5. **ซ่อมรูปเล่มด้วย caption field** ให้เลขรูป/ตารางกลับเป็น 3.x และ 4.x แล้วขยาย Diagram/หน้าจอที่อ่านไม่ออก

> ถ้าเวลาน้อย ให้ทำข้อ 1–4 ก่อน ส่วนการเกลาภาษาและความสวยงามทำเป็นรอบท้าย

## คำตัดสินภาพรวม

**ต้องแก้สาระสำคัญก่อนส่งหรือสอบ — แก้ได้โดยใช้แผน 5 รอบท้ายรายงาน**

ตัวระบบมีขอบเขตฟังก์ชันค่อนข้างชัดและบทที่ 4 แสดงหน้าจอครบหลายบทบาท ซึ่งเป็นฐานที่นำมาแก้ต่อได้ดี สิ่งที่ยังขาดคือหลักฐานสำหรับข้อสรุปเชิงวิศวกรรมและเชิงวิจัย โดยเฉพาะความเที่ยงตรงของวิธีแปลงเกรดเป็นระดับทักษะ ความสอดคล้องของสถาปัตยกรรม Express.js/SvelteKit กับ baseline ความถูกต้องของบรรณานุกรม การอ้างอิงในตัวบท และการทดสอบ API ประเด็นเหล่านี้แก้ได้ด้วยการทำสิ่งที่อนุมัติไว้ให้ครบ ลดคำกล่าวอ้างให้ตรงข้อมูล ตรวจแหล่งต้นฉบับ และจัดหลักฐานทดสอบใหม่ โดยไม่ต้องเปลี่ยนขอบเขตเดิม

## ความเห็นโดยละเอียด

### A. ระเบียบวิธี แกนกลางของระบบ และความน่าเชื่อถือ

#### METH-01 — การแปลงเกรดเป็น “ระดับทักษะจริง” ยังไม่มีความเที่ยงตรง

- ระดับ: **Critical**
- ตำแหน่ง: PDF 25–33 / เล่ม 8–16; PDF 76 / เล่ม 59; PDF 104–109 / เล่ม 87–92
- สิ่งที่พบ: ระบบนำเกรดรายวิชา 0–4 ไปปรับสเกลตามระดับสูงสุดของ Bloom แล้วเปรียบเทียบกับเกณฑ์อาชีพ จากนั้นใช้ถ้อยคำว่าเป็นระดับทักษะจริง ถูกต้อง แม่นยำ ยุติธรรม และปราศจากอคติ
- หลักฐาน: เกรดรายวิชาเป็นคะแนนรวมจากหลายผลลัพธ์การเรียนรู้ ไม่ได้พิสูจน์ว่าผู้เรียนทำทักษะแต่ละรายการได้ในระดับเดียวกัน ส่วนระดับ Bloom เป็นระดับกระบวนการคิดของกิจกรรมหรือผลลัพธ์การเรียนรู้ ไม่ใช่หน่วยวัดความชำนาญโดยอัตโนมัติ
- ผลกระทบ: ผล gap analysis อาจดูเป็นตัวเลขที่แม่นยำ แต่ไม่มี construct validity รองรับ ทำให้ข้อสรุปหลักของโครงงานอ่อนลง
- แนวทางแก้:
  1. เปลี่ยนถ้อยคำจาก “ระดับทักษะจริง” เป็น “ค่าประมาณระดับทักษะจากผลการเรียน” จนกว่าจะมีการพิสูจน์
  2. นิยามตัวแปรทุกตัว หน่วย ช่วงค่า และเหตุผลที่เลือกสมการ
  3. แสดงตัวอย่างคำนวณตั้งแต่เกรด–รายวิชา–ทักษะ–ระดับ Bloom–เกณฑ์อาชีพ–ค่าช่องว่างอย่างน้อย 2 กรณี รวมกรณีขอบเขต
  4. สร้างเกณฑ์อ้างอิงจาก rubric งานปฏิบัติหรือคะแนนผู้เชี่ยวชาญ แล้วเปรียบเทียบผลระบบกับ ground truth
  5. รายงาน MAE/RMSE หรือ agreement ตามชนิดข้อมูล พร้อม confidence interval และวิเคราะห์กรณีผิดพลาด
  6. ทำ sensitivity analysis ว่าเมื่อ mapping รายวิชา–ทักษะหรือระดับ Bloom เปลี่ยน ผลลัพธ์เปลี่ยนมากเพียงใด

- ฉบับขั้นต่ำที่ควรแก้: ลดคำว่า “ทักษะจริง/ปราศจากอคติ” เป็น “ค่าประมาณจากผลการเรียน” ทำตัวอย่างคำนวณ และเขียนข้อจำกัดให้ชัด หากยังไม่มีเวลาเก็บ ground truth ใหม่
- อ่านต่อ:
  - [Standards for Educational and Psychological Testing](https://www.testingstandards.net/uploads/7/6/6/4/76643089/9780935302356.pdf) — อ่านบท Validity เพื่อเข้าใจว่าการตีความคะแนนต้องมีหลักฐานรองรับ แล้วนำหลักนี้ไปเขียนข้อจำกัดของวิธีในบทที่ 2, 3 และ 5
  - [MinMaxScaler documentation](https://scikit-learn.org/stable/modules/generated/sklearn.preprocessing.MinMaxScaler.html) — ใช้ตรวจสูตรและช่วงค่าในบทที่ 2 แต่ต้องจำไว้ว่า normalization เปลี่ยนสเกล ไม่ได้พิสูจน์ว่าคะแนนวัด “ทักษะจริง”

#### METH-02 — SFIA 7 ระดับกับ Bloom 6 ระดับยังเชื่อมกันไม่ชัด

- ระดับ: **Critical**
- ตำแหน่ง: PDF 25–30 / เล่ม 8–13
- สิ่งที่พบ: เล่มนำ SFIA และ Bloom มาใช้ร่วมกัน แต่ไม่พบตาราง mapping ระหว่างกรอบทั้งสอง และไม่อธิบายว่า “ระดับความรับผิดชอบ” ของ SFIA เท่ากับ “ระดับพุทธิพิสัย” ได้อย่างไร
- ผลกระทบ: การเปรียบเทียบความสามารถนักศึกษากับความต้องการของอาชีพอาจเป็นการเทียบคนละมิติ
- แนวทางแก้: ระบุว่ากรอบใดใช้กับตัวแปรใด แยก cognitive complexity ออกจาก proficiency/responsibility ถ้าจำเป็นต้องเชื่อมกันให้สร้าง mapping rubric ผ่านผู้เชี่ยวชาญและรายงานวิธีหาความตรงเชิงเนื้อหา เช่น IOC/CVI พร้อมเกณฑ์ตัดสิน
- ฉบับขั้นต่ำที่ควรแก้: ทำตาราง 3 คอลัมน์ว่า Bloom ใช้วัดอะไร, SFIA ใช้อธิบายอะไร และระบบนำค่าทั้งสองมาเชื่อมกันด้วยกฎใด หากยังไม่มีหลักฐานรองรับกฎ ให้บอกว่าเป็นสมมติฐานของต้นแบบ
- อ่านต่อ: [SFIA 9 — Levels of responsibility](https://sfia-online.org/en/sfia-9/responsibilities) อธิบายว่า 7 ระดับของ SFIA เน้นความรับผิดชอบ ความรับผิดรับชอบ และผลกระทบในการทำงาน ให้นำคำจำกัดความนี้ไปตรวจว่ากำลังเทียบกับ Bloom คนละมิติหรือไม่

#### METH-03 — แหล่งที่มาของ skill benchmark อาชีพยังไม่ตรวจสอบได้

- ระดับ: **Major**
- ตำแหน่ง: PDF 19–20 / เล่ม 2–3; PDF 54–60 / เล่ม 37–43; PDF 86–94 / เล่ม 69–77
- สิ่งที่พบ: ระบบเปิดให้อาจารย์กำหนดสายอาชีพและระดับทักษะ แต่ยังไม่พบวิธีคัดเลือกผู้เชี่ยวชาญ จำนวนผู้เชี่ยวชาญ วันที่อ้างอิงตลาดแรงงาน หรือกระบวนการทบทวนเกณฑ์
- ผลกระทบ: “ช่องว่างทักษะ” จะเชื่อถือไม่ได้ถ้าค่าความต้องการของอาชีพเป็นความเห็นของผู้กำหนดเพียงคนเดียว
- แนวทางแก้: อธิบายแหล่งข้อมูลตำแหน่งงาน กรอบมาตรฐาน วันที่เก็บข้อมูล เกณฑ์รวม/ตัดทักษะ และกระบวนการฉันทามติของผู้เชี่ยวชาญ รวมทั้ง versioning ของ benchmark

- ผลกระทบ: ผู้อ่านยังไม่รู้ว่างานสำเร็จในระดับใด และบทคัดย่อไม่ทำหน้าที่เป็นบทสรุปจบในหน้าเดียว
- แนวทางแก้: เขียนใหม่เป็น 5 ส่วนในย่อหน้าเดียวหรือ 2 ย่อหน้า ได้แก่ ปัญหาและช่องว่าง → วัตถุประสงค์ → วิธีและข้อมูล → ผลเชิงตัวเลข → คุณค่าและข้อจำกัด
- ตัวอย่างโครงข้อความ:

  “โครงงานนี้พัฒนา…เพื่อแก้ปัญหา… ระบบใช้…ในการประมาณ… และได้รับการทดสอบด้วย test case จำนวน [N] กรณี ครอบคลุม [โมดูล] ผลการทดสอบผ่าน [x/N] กรณี มีเวลาตอบสนองมัธยฐาน [ค่า] มิลลิวินาที และประเมินการใช้งานกับผู้ใช้ [N] คน โดยได้คะแนน SUS [ค่า]/100 หรือคะแนนความพึงพอใจเฉลี่ย [ค่า ± SD] ผลดังกล่าวชี้ว่า… อย่างไรก็ตาม ผลทักษะเป็นค่าประมาณจากเกรดและยังต้องตรวจสอบกับผลประเมินภาคปฏิบัติ…”

  ต้องแทนค่าทุกช่องด้วยผลจริง ห้ามสร้างตัวเลขขึ้นเอง

  5. ตรวจบทที่ 1, 3, 4, 5 ด้วยคำค้น Express, REST, form action และ server-side แล้วทำตาราง “ข้อกำหนดเดิม → หลักฐานการทำครบ/หลักฐานอนุมัติเปลี่ยน → ตำแหน่งในเล่ม”

#### UX-01 — บทออกแบบ UX/UI แสดงผลลัพธ์หน้าจอรวม แต่ไม่แสดงกระบวนการออกแบบ

- ระดับ: **Major**
- ตำแหน่ง: PDF 61–64 / เล่มหน้า 44–47

#### DB-01 — ER Diagram และ Data Dictionary ยังตรวจข้อจำกัดข้อมูลได้ไม่ครบ

- ระดับ: **Major**
- ตำแหน่ง: PDF 64–69 / เล่มหน้า 47–52
- สิ่งที่พบ:
  - ER Diagram ตัวเล็กจน cardinality และชื่อ field อ่านยาก
  - ตารางเชื่อม Course_skills, Job_skills และ Student_grades ไม่ระบุ composite primary key/unique constraint ชัดเจน
  - หัวข้อ foreign key ของ Course_skills กล่าวถึง skill_id แต่ไม่กล่าวถึง course_id
  - Data Dictionary ไม่มี nullability, default, unique, check constraint, index, on update/delete และเหตุผลชนิดข้อมูล
  - Student_grades ไม่มีภาคเรียน ปีการศึกษา หรือครั้งที่ลงทะเบียน จึงรองรับประวัติเกรดซ้ำได้ไม่ชัด
  - Users เก็บ grade_letter และ grade_point ซ้ำกัน เสี่ยงข้อมูลไม่ตรง
  - Job.name_job เป็น VARCHAR(20) ซึ่งสั้นเกินไปสำหรับหลายชื่อตำแหน่ง
- แนวทางแก้: วาด ER ใหม่พร้อม cardinality/optionality ระบุ PK/FK/UK และ business rules แล้วขยาย Data Dictionary ให้ครบ constraint พร้อมตัวอย่าง SQL DDL หรือ migration ที่ตรงกับระบบจริง
- ฉบับขั้นต่ำที่ควรแก้: ระบุ primary key/foreign key/unique/nullability ของทุกตารางเชื่อม อธิบายเหตุผลเก็บ grade_letter กับ grade_point และเพิ่มภาคเรียน/ปีการศึกษาหากระบบต้องเก็บประวัติ
- อ่านต่อ: [MySQL 8.4 — FOREIGN KEY Constraints](https://dev.mysql.com/doc/refman/8.4/en/create-table-foreign-keys.html) ใช้ตรวจชนิดข้อมูลของคีย์ ความเข้ากันได้ของ index และพฤติกรรม ON DELETE/ON UPDATE ก่อนแก้ Data Dictionary

#### API-02 — ความหมาย HTTP 401/403 และเลขหัวข้อผิด

- ระดับ: **Minor**
- ตำแหน่ง: PDF 70–71 / เล่มหน้า 53–54
- สิ่งที่พบ: 401 อธิบายกว้างว่าไม่ได้รับอนุญาต ส่วน 403 เขียนไม่ครบ ความหมายที่ควรใช้คือ 401 = ยังไม่ผ่าน/ไม่มีข้อมูลยืนยันตัวตนที่ใช้ได้ และ 403 = ยืนยันตัวตนแล้วแต่ไม่มีสิทธิ์ทำรายการ อีกทั้งเลขหัวข้อ 3.1.7.1–3.1.7.2 ควรตรวจให้ตรงกับ 3.7
- แนวทางแก้: แก้คำจำกัดความและเลขหัวข้ออัตโนมัติทั้งชุด
- อ่านต่อ: [RFC 9110 — HTTP Semantics](https://www.rfc-editor.org/rfc/rfc9110.html#name-401-unauthorized) อ่านหัวข้อ 401 และ 403 แล้วใช้ถ้อยคำจากความหมายมาตรฐานในการแก้ตาราง 3.12

- ตำแหน่ง: PDF 71–75 / เล่มหน้า 54–58 และ PDF 99–103 / เล่มหน้า 82–86

- ตำแหน่ง: PDF 97–98 / เล่มหน้า 80–81
- สิ่งที่พบ: ตารางแสดง endpoint, method และ status code เท่านั้น ไม่ระบุ payload, expected response, assertion, environment, จำนวนรอบ, response time, concurrent users, error rate หรือ security attack cases
- ผลกระทบ: status 200/201 เพียงครั้งเดียวไม่ใช่หลักฐาน performance, reliability หรือ security ส่วน 401 ไม่พิสูจน์ว่า authorization ทุกบทบาทถูกต้อง

  5. รายงานเครื่องมือ เวอร์ชัน สเปกเครื่อง ฐานข้อมูล และจำนวนรอบเพื่อทำซ้ำได้

## แบบการประเมินที่แนะนำให้ใช้แทน/เพิ่ม

### 1. Functional testing

- แยก test suite ตาม Scope ID และ actor
- ทุกกรณีมี Test ID, precondition, input, steps, expected, actual, pass/fail, evidence และ defect
- ครอบคลุม happy path, boundary, invalid format, duplicate, unauthorized, concurrent update, database unavailable และ recovery

### 2. Validation ของการคำนวณทักษะ

- สร้างชุดตัวอย่างที่ผู้เชี่ยวชาญให้ค่าทักษะอ้างอิงจากหลักฐานปฏิบัติ
- ใช้ผู้เชี่ยวชาญมากกว่าหนึ่งคนและรายงานเกณฑ์ฉันทามติหรือ inter-rater agreement
- เปรียบเทียบค่าระบบกับค่ามาตรฐานด้วย metric ที่เหมาะสม
- วิเคราะห์ false high/false low และสาเหตุ
- ทดสอบผลกระทบของเกรดซ้ำ รายวิชาที่ mapping หลายทักษะ และการเปลี่ยนระดับ Bloom

### 3. Usability evaluation

- จำนวนรวม 30 คนขึ้นไปใช้ได้ในฐานะการทดสอบเชิงสำรวจ แต่ต้องแบ่งตาม actor และรายงาน n ต่อ task/ข้อ
- อาจารย์ 2 คนและผู้ดูแล 3 คนยังน้อยเกินไปสำหรับการสรุปกว้าง ควรเพิ่มผู้ใช้ในบทบาทดังกล่าว หรือระบุว่าเป็น expert walkthrough/qualitative formative evaluation
- ให้ผู้ใช้ทำ task จริง เช่น เลือกอาชีพ ดู gap หาเหตุผลของคะแนน แก้ mapping และ export ข้อมูล
- เก็บ task success, completion time, error count, assistance count และ SUS/UMUX-Lite
- เก็บความเห็นปลายเปิด สกัด theme และระบุสิ่งที่ปรับแก้จากผล

### 4. Performance และ security

- กำหนด workload และเกณฑ์ก่อนทดสอบ เช่น p95 latency, throughput, error rate และจำนวน concurrent users
- ทดสอบ authorization matrix ทุก endpoint และทุกบทบาท
- ตรวจ OWASP-relevant cases อย่างน้อย injection, broken access control, session/CSRF, sensitive data exposure, rate limit และ export authorization
- รายงาน environment, versions, seed data, tool/script และวิธีทำซ้ำ

## แผนแก้เล่มแบบเป็นรอบ

### รอบที่ 1 — หยุดความเสี่ยงด้านความถูกต้อง

1. ตรวจบรรณานุกรมทั้ง 24 รายการจาก DOI/ผู้จัดพิมพ์และเขียนบทงานวิจัยใหม่จากต้นฉบับ
2. ใส่ citation ในตัวบททุกนิยาม สมการ รูป สถิติ และข้อค้นพบ
3. กำหนดสถานะของค่าทักษะว่าเป็น “ค่าประมาณ” และออกแบบ validation
4. ทำ Express.js ให้ครบตาม baseline หรือแนบหลักฐานการอนุมัติเปลี่ยนเป็น SvelteKit แล้วทำบทที่ 2–5 ให้ตรงกับ baseline ฉบับอนุมัติ

### รอบที่ 2 — ทำบทที่ 3 ให้เป็นงานออกแบบ

1. ทำ requirement traceability, conceptual/component/deployment diagram
2. ตรวจ Context/DFD balancing และขยายรูปให้อ่านได้
3. วาด ER พร้อม constraints และแก้ Data Dictionary
4. เพิ่ม UX process: flow, IA, wireframe, states, accessibility และภาพมี callout
5. ทำ API contract และ threat model

### รอบที่ 3 — สร้างหลักฐานบทที่ 4

1. ทำ test case ตามขอบเขตทุกข้อ
2. ทดสอบ calculation validity แยกจาก usability
3. ทำ API functional, performance และ security tests พร้อมข้อมูลดิบ
4. ตรวจข้อมูลผู้ตอบ 35 คนใหม่ รายงาน n, SD และการกระจาย
5. เพิ่มกราฟและสรุป feedback ที่นำไปแก้ระบบ

### รอบที่ 4 — เขียนส่วนต้นและบทที่ 5 ใหม่

1. เขียนบทคัดย่อไทยจากผลจริง แล้วแปล/ตรวจเทียบอังกฤษ
2. เขียนบทที่ 5 ตามวัตถุประสงค์และขอบเขต พร้อมตาราง completed/partial/not completed
3. อภิปรายผลเทียบทฤษฎีและงานวิจัย ไม่กล่าวเกินหลักฐาน
4. ระบุข้อจำกัดและ threat to validity

### รอบที่ 5 — ตรวจรูปเล่มก่อนส่ง

1. ซ่อม caption/field แล้ว update สารบัญทั้งหมด
2. ขยาย Diagram, ER และภาพหน้าจอให้ตัวหนังสืออ่านได้ พร้อม label
3. ตรวจคำศัพท์ คำย่อ เชิงอรรถ อภิธานศัพท์ และคำผิดจากตารางข้างต้น
4. ตรวจเลขหน้า cross-reference ลิงก์ QR code และข้อมูลส่วนบุคคล
5. export PDF ใหม่และตรวจแบบ page-by-page อีกหนึ่งรอบ

- [ ] อธิบายการเก็บ/หมดอายุ/ใช้ครั้งเดียว/rate limit ของ OTP และตรวจข้อมูลส่วนบุคคล (DB-02)
- [ ] เพิ่ม API contract: request, response, validation, role, error และตัวอย่าง (API-01)
- [ ] แยกแผนทดสอบ correctness, validity, performance, security และ usability (EVAL-01/EVAL-03)
- [ ] ตรวจจำนวนคำถามแบบประเมินให้เป็นฉบับเดียวกัน 28 หรือ 29 ข้อ (EVAL-02)

### บทที่ 4 ผลการพัฒนาและผลทดลอง

- [ ] เปิดบทด้วย traceability: Scope ID → Design → Test → Evidence → Result (TRACE-01)
- [ ] เปลี่ยนภาพหน้าจอสำคัญให้เป็น flow พร้อม input/action/expected/actual/pass-fail (CH4-01)
- [ ] ใส่ callout 1, 2, 3 บนภาพจริงและขยายข้อความ UI ให้อ่านได้
- [ ] เพิ่ม API test case ทั้ง valid, invalid, unauthorized และ role matrix (TEST-01)
- [ ] ทดสอบ logout ให้ครบ endpoint ที่ออกแบบไว้ หรือแก้จำนวน endpoint (TEST-02)
- [ ] รายงาน x/N และจำนวนรอบแทนคำว่า “100%” ที่ไม่มีตัวหาร (TEST-03)
- [ ] เรียก CSV ว่า export; ถ้าจะเรียก backup ต้องมี restore test (TEST-04)
- [ ] ตรวจข้อมูลผู้ตอบ 35 คนและแก้ร้อยละอุปกรณ์ให้กลับเป็นจำนวนคนเต็ม (DATA-01)
- [ ] รายงาน n, mean, SD/การกระจาย และแยกนักศึกษา–อาจารย์–ผู้ดูแล (DATA-02)
- [ ] แก้เกณฑ์ช่วงคะแนนที่ซ้ำ/ขัดกัน (DATA-03)
- [ ] เพิ่มกราฟที่มีแกน หน่วย n และสรุป feedback → สิ่งที่ปรับระบบ (DATA-04)
- [ ] ใช้ผลความพึงพอใจสรุปเฉพาะการรับรู้ของผู้ใช้ ไม่ใช้ยืนยันความแม่นยำ/ปลอดภัย (DATA-05)

### บทที่ 5 สรุปและข้อเสนอแนะ

- [ ] สรุปทีละวัตถุประสงค์ด้วยหลักฐานและตัวเลขจากบทที่ 4
- [ ] เพิ่มตาราง scope ทั้งหมด/ครบ/บางส่วน/ไม่พบหลักฐาน พร้อม Test ID (CH5-01)
- [ ] อภิปรายว่าผลสอดคล้องหรือขัดกับทฤษฎีและงานวิจัยใด เพราะอะไร (CH5-02)
- [ ] ตัดคำกล่าวเรื่องลด latency/เพิ่ม security หากไม่มี benchmark หรือเพิ่มการทดลอง (CH5-03)
- [ ] เขียนข้อจำกัดเรื่องกรอกเกรดและ expert mapping แล้วลดระดับข้อสรุปให้ตรงกัน (CH5-04)
- [ ] ตรวจให้ตัวเลขสำคัญตรงกับบทคัดย่อและบทที่ 4

### บรรณานุกรมและงานวิจัย

- [ ] ตรวจรายการทั้ง 24 ชิ้นจาก DOI/หน้าผู้จัดพิมพ์ ไม่แก้เฉพาะ 4 ตัวอย่างที่รายงานพบ (REF-01)
- [ ] แก้ชื่อ ผู้แต่ง ปี วารสาร/ประชุม เล่ม ฉบับ หน้า และ DOI ให้ตรง
- [ ] ตรวจรายการหมายเลข 14 เพิ่ม; หากหาต้นฉบับไม่ได้ให้เปลี่ยนแหล่งหรือแสดงหลักฐาน
- [ ] ตรวจว่า citation ทุกหมายเลขถูกเรียกใช้ในเนื้อหาและไม่มีรายการเกิน
- [ ] ใช้แหล่งต้นฉบับ/ทางการแทน blog, GitHub Topics หรือภาพจากเว็บทั่วไปเมื่อทำได้ (REF-03)
- [ ] ระบุผลเชิงตัวเลขและข้อจำกัดของงานที่เกี่ยวข้อง ไม่สรุปเพียงหัวข้อกว้าง

### ภาษา รูป Diagram และรูปเล่ม

- [ ] ซ่อม caption field ให้รูป/ตารางเป็นเลข 3.x และ 4.x แล้ว Update all fields (FMT-01)
- [ ] แก้เลขหัวข้อ 3.1.7.1/3.1.7.2 และ HTTP 401/403 (API-02)
- [ ] แก้คำผิดจากตารางรายการคำผิดด้วย Find/Replace แบบตรวจบริบท
- [ ] กำหนดคำไทย–อังกฤษ–คำย่อครั้งแรกและใช้รูปเดียวทั้งเล่ม (TERM-01)
- [ ] ทำอภิธานศัพท์/ประมวลศัพท์ และใช้เชิงอรรถเฉพาะคำที่ต้องอธิบาย ณ หน้านั้น (TERM-02)
- [ ] ตรวจว่าทุกรูปอ่านได้ที่ขนาดพิมพ์จริง มี source/caption และถูกกล่าวถึงในเนื้อหา
- [ ] ตรวจ QR code, repository/tag/commit และความยินยอมก่อนเผยข้อมูลส่วนบุคคล (APP-01)
- [ ] Export PDF ใหม่แล้วให้สมาชิกที่ไม่ได้จัดหน้าเปิดตรวจทุกหน้าหนึ่งรอบ

## เกณฑ์พร้อมส่งรอบถัดไป

เล่มควรกลับมาตรวจรอบใหม่เมื่อมีครบอย่างน้อยดังนี้:

- บรรณานุกรมและ citation ตรวจจากต้นฉบับครบ
- วิธีคำนวณลดระดับคำกล่าวอ้างหรือมี validation รองรับ
- สถาปัตยกรรมตรงกับ baseline ที่อนุมัติและตรงกันทุกบท
- Traceability matrix และ test case ครบขอบเขต
- ผล API มี expected/actual และหลักฐาน performance/security ตามที่อ้าง
- ผลประเมินมี n ต่อข้อ, SD/การกระจาย และแก้ข้อมูลร้อยละอุปกรณ์
- Diagram/ER/UX อ่านได้ที่ขนาดพิมพ์จริงและมีคำอธิบายทีละส่วน
- บทคัดย่อมีผลเชิงตัวเลข และบทที่ 5 มีตารางสรุปขอบเขต
- หมายเลขรูป ตาราง หัวข้อ และคำผิดถูกแก้ทั้งเอกสาร
